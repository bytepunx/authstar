## Decisions

- The planner's eight tasks (TH-0025) are kept as drafted. They fit the criteria and the three ADRs, and their touches are named file by file.
- Layers, as the planner set them:
  - Layer 1: T-0062 and T-0064 run together. They wait for nothing and share no path.
  - Layer 2: T-0070 waits for T-0062. Both change `plan_mapping_actor.ts`, `routes/plan-mappings.ts`, and `webhooks.ts`.
  - Layer 3: T-0073 waits for T-0070. Both change `subscription_actor.ts` and `webhooks.ts`.
  - Layer 4: T-0076 waits for T-0064, for the threshold, and for T-0073, for the status union and the shared files.
  - Layer 5: T-0080 waits for T-0076, for the degrade and restore helper.
  - Layer 6: T-0083 waits for T-0080. Its guard covers every handler before it, and its test replays their events.
  - Layer 7: T-0084 waits for T-0083. It documents the finished behaviour.
- Six of the tasks change `webhooks.ts`, so layers 2 to 7 run one after another. Each is handed to one task sub-agent.
- T-0064 stores `paymentFailureAttempts` as one more entry in keep's own signet bundle, `stripe-payment-failure-attempts-<slug>`, beside the two Stripe secrets. That bundle is the only store the module writes, and `server.ts` already reloads it at startup. Signet config would suit a non-secret better, but it needs new wiring in `server.ts`. An actor would contradict Story 001's "stripe-config is not an actor". An unreadable stored value reads as unset, so the threshold is 3. `effectivePaymentFailureAttempts(store, tenant)` in `lib/stripe-config.ts` is the reader for T-0076.
- T-0062 keeps a legacy read in `plan_mapping_actor.ts`: an event persisted before the rename carries `grantedRoles`, so it still replays. `grep grantedRoles keep/src` also finds the coupons' and trials' own `grantedRoles` fields. ADR-0108 renames only the plan mapping's field, so those stay.
- Web still reads `grantedRoles` from keep (`web/src/lib/server/clients/keep.ts:28`, `web/src/routes/(admin)/billing/plan-mappings/+page.svelte:37`, on main and on `story/S-0008`). MS-0019 asks S-0008 whether it switches web to `roles`. Until it answers, keep returns `roles` only, as ADR-0108 says. `toResponse()` in `routes/plan-mappings.ts` is the one place an output alias would go.
- T-0070 drops the `{tenant}` fallback from the webhooks. A subscription with neither an account nor an organization scope, in its metadata or on its known customer, is not recorded and publishes nothing; keep logs a `warn`. A refund or dispute with no such scope is still recorded, with `scope: null`, and changes no entitlement. That follows T-0080's "recorded with no subscription", not ADR-0107's "the tenant as scope", which ADR-0109 retired. `scopesEqual` still compares a legacy `{tenant}` record, which only `billing-reads.ts` asks for.
- T-0070's touches were widened to `entitlement-publisher.ts` and `consequent-sequence-provider.spec.ts`: `EntitlementScope` and the seat-limit event's scope no longer admit `{tenant}`, and the sequence spec uses `{organization}`.
- Plan mappings in T-0070 needed no `{tenant}` refusal. They carry no scope, and their schema already refuses one.
- T-0076's one helper is `setEntitlement(app, tenant, stripeSubscriptionId, target)` in `webhooks.ts`. It no-ops in the target state and restores only an `active` or `trialing` subscription. A record from before T-0076 has no `entitlement` field. It reads as degraded when canceled, unpaid, or paused, because the old code had already revoked those roles, and as granted otherwise. When `invoice.paid` arrives before the `updated` to `active`, keep reads the status from Stripe first, so that the restore is not lost to event order.
- `invoice.paid` restores any degraded subscription that is `active` or `trialing`, one degraded by a dispute included. That follows ADR-0107 as written, and a later `won` is then a no-op. Holding a dispute's degrade against a paid invoice would need a new rule, and none is decided.
- T-0083's task sub-agent also closes the double activation: `customer.subscription.created` and `checkout.session.completed` for one subscription each publish its grants today. The goal says a duplicated event publishes nothing a second time.
- T-0084's live run found the `createPortalSession` case failing with 403 (I-0011, recorded on `story/S-0008`): it sent a pre-ADR-0100 token. 0b07678 sends the organization membership `requireOrganizationAccess` checks, and all 13 live tests pass. S-0008 leaves I-0011 open until the fix is on main (MS-0019). Close I-0011 at S-0005's acceptance, naming 0b07678, or at S-0008's sync if S-0008 lands second.
- T-0135 was added after the planner's eight. The living webhook contract, `design/stories/keep/002-stripe-webhook-handling.md`, still described the immediate revoke and `grantedRoles`. S-0007 changes that file too, in a different section. Only the `updated` line conflicts, and the later date wins (MS-0021).
- `design/system/overview.md` line 72 says webhooks have no event-id idempotency. It sits under the dated "State on 2026-10-21" section, a snapshot, so S-0005 leaves it alone.
- In the shared paths (MS-0010), S-0005 adds beside S-0008's lines. `docs/users/index.md` gets its own note on degrade, beside S-0008's "Plan mappings" section, not inside it.
