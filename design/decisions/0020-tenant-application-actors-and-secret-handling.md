# ADR 0020: Tenant and Application Actors; Secrets Never Persisted in Tower's Event Log

- **Status:** Accepted (extended by [ADR 0062](0062-tenant-status-enforcement-and-reactivation.md), [ADR 0064](0064-portal-signin-flow.md))
- **Date:** 2026-07-24
- **Affects:** tower

> **Extended:** `tenant` gains `seatLimit` (ADR 0031), and later `branding: { name, logoUrl,
> primaryColor }` (ADR 0064) — non-secret, flows into portcullis's bundle the same way
> `providers`/`cookie` already do.

## Context

`tenant` and `application` had been referenced throughout prior ADRs (`account.tenant`,
`invite.tenant`/`application`, portcullis's bundle shape in Story 001) without ever being
specified as actual consequent actors. Specifying them surfaced a real question: does tower's
event-sourced log ever durably store secret material (provider `clientSecret`, the per-tenant
signing keypairs), or does it strictly defer to signet as the sole secrets authority (ADR 0004)
and never persist secret values itself?

## Decision

### `tenant` actor

Identified by `slug` directly — already the natural unique key used throughout portcullis's
config.

```ts
{
  actor: { namespace: 'tower', type: 'tenant', identifiedBy: 'slug', searchableBy: ['status'] },
  state: {
    slug: '', name: '', status: 'active',   // active | suspended | deleted
    providers: {},   // name -> { discoveryUrl, scope } -- non-secret metadata only
    cookie: { domain: '', path: '/', maxAge: 604800, httpOnly: true, secure: true },
    createdAt: '', createdBy: '',
  }
}
```

### `application` actor

Identified by a generated id; `tenant`/`slug` are searchable (listing "every application for
tenant X" is a `find()`-backed, eventually-consistent-tolerant admin/aggregation operation, not
a hot-path lookup — same reasoning already applied to `account`'s `searchableBy` in ADR 0017).

```ts
{
  actor: { namespace: 'tower', type: 'application', identifiedBy: 'appId',
           searchableBy: ['tenant', 'slug', 'status'] },
  state: {
    tenant: '', slug: '', name: '', status: 'active',
    hosts: [], publicUrl: '',
    upstream: { base: '', routes: {}, timeout: 30 },
    cors: { origin: [] }, exempt: [],
    auth: { loginUrl: '/oauth2/select' },
    exposedProviders: [],   // ordered names, referencing tenant.providers
  }
}
```

### Secrets are never durably stored in tower's own event log

Signet (ADR 0004) is the sole secrets authority for the whole system. Tower's Postgres-backed
event log holding a second, durable copy of provider `clientSecret`s or signing private keys
would create exactly the inconsistent-duplicate-store problem ADR 0004 exists to avoid. So the
mechanics for config vs. secrets diverge:

- **Non-secret config** (hosts, upstream, CORS, exempt, provider metadata) is aggregated by a
  `portcullisBundle` view actor — one per tenant, sourced from that tenant's and its
  applications' events — into the shape Story 001 defines. A change to this view is what
  triggers a `SyncBundle` push (ADR 0009/0011).
- **Secrets** (provider `clientSecret`, the two per-tenant signing keypairs — ADR 0002) are
  pushed to signet **immediately, at the moment they're set or rotated**, not derived from
  replaying tower's event log later, since the log was never given the value to replay. Tower's
  own event for that action records that a rotation happened (who, when, a key fingerprint for
  audit) — never the secret's value. Signing keypairs are generated by tower at tenant creation
  or explicit rotation and transit tower's process memory only transiently before being pushed.

### Consequence for event replay

Replaying tower's full event history reconstructs all non-secret domain state exactly, but
secret-bearing fields are **not** reconstructable from tower's own log by design — they always
come from signet, never from replay. Deliberate, not an oversight, and load-bearing for how key
rotation and provider secret management get implemented from here on.

## Consequences

- Tower needs the `portcullisBundle` view actor described above.
- Tower needs a distinct code path for secret-affecting admin actions (set/rotate a provider
  secret, rotate a tenant's signing keys) that pushes to signet directly at action time, separate
  from the ordinary event-sourced config flow.
