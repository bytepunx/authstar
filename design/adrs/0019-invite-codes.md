# ADR 0019: Invite Codes as a Distinct, Multi-Redemption Mechanism

- **Status:** Accepted
- **Date:** 2026-07-24
- **Affects:** tower
- **Extends:** [ADR 0018](0018-trial-roles-and-keep-boundary.md), the invite discussion preceding it

> **Corrected 2026-08-02 ([ADR 0082](0082-tower-actor-boundary-corrections.md)):**
> `inviteCode.identifiedBy` below is the bare `code` field — read literally, that means
> globally unique across every tenant, a real collision risk for human-chosen, memorable codes
> this ADR explicitly wanted. Corrected to a composite `{tenant}:{code}` key.

## Context

The targeted `invite` actor (single email, single use, email-match-gated at acceptance) doesn't
cover a common, distinct pattern: an admin-issued, publicly-shareable code — posted on social
media, handed out by a speaker at a conference, given to a salesperson, or generated by an
ordinary user to refer friends. These need multi-redemption (or a capacity cap, not
strictly-one-use), no target email to check, and issuance by accounts that aren't necessarily
admins.

Separately: should coupon codes (discounts, free entitlements) be modeled in tower at all, or
does keep own that entirely?

## Decision

`inviteCode` — a new, distinct actor.

### `inviteCode` — a new, distinct actor

```ts
{
  actor: { namespace: 'tower', type: 'inviteCode', identifiedBy: 'code',
           searchableBy: ['issuedBy', 'tenant', 'status'] },
  state: {
    code: '',                  // the redeemable string -- see naming note below
    tenant: '',
    application: '',            // optional; tenant-wide if omitted
    issuedBy: '',                 // accountId
    roles: [],                     // {name, scope} grants applied on redemption
    trialDurationDays: null,        // if set, grants go to the redeemer's trialRoles with a
                                      // computed expiresAt (ADR 0018); if null, they go to
                                      // grantedRoles permanently
    maxRedemptions: null,             // null = unlimited
    redemptionCount: 0,
    status: 'active',                  // active | revoked | expired
    expiresAt: null,
  }
}
```

Unlike `invite`'s long random token (single-recipient, sent as a link), `code` should support
an issuer-chosen, human-readable value (e.g. `SPEAKERJOHN`, `LAUNCH50`) as well as an
auto-generated one — memorability matters when the whole point is verbal/social sharing.
Uniqueness is enforced at creation (a duplicate business key fails outright, consequent's
normal behavior).

### Redemption

Same identity-resolution flow as `invite` — the redeemer authenticates normally, tower
resolves-or-creates their account, *then* checks the code (`status: active`, not expired,
`redemptionCount < maxRedemptions`) and applies `roles` to `grantedRoles` or `trialRoles`
depending on `trialDurationDays`, incrementing `redemptionCount`. No email-match check, since
there's no target email. Consequent's per-actor command queuing serializes concurrent
redemption attempts against the same code, so the capacity check can't race.

### Issuance is gated by `permissions` — generalized beyond admin-only

ADR 0018 introduced `permissions` as a tower-owned authorization primitive (distinct from
opaque, app-interpreted `roles`) for gating tower's own operations. This extends it: a
`permissions` grant is not inherently admin-exclusive — it's a general capability grant, and
`invite:code:issue` can be held by any account, admin or not:

```ts
{ grant: 'invite:code:issue', scope: 'tenant' | { application: '' }, maxOutstanding: null }
```

This one mechanism covers all three cases raised:
- **App admin**, broad distribution: wide scope, high/no `maxOutstanding`.
- **Referral-enabled regular users**: a narrow grant (an application's own logic decides who
  gets it — possibly baked into a default role at signup), small `maxOutstanding` (e.g. 3).
- **Speakers/salespeople**: an application-defined role paired with this permission grant,
  possibly with its own `roles`-to-grant and higher `maxOutstanding` for promotional purposes.

`maxOutstanding` is enforced by tower locally at issuance time — an anti-abuse limit, unrelated
to any billing concern, same category as the invite quota discussed earlier.

### Coupon codes are entirely keep's domain — no new tower machinery

A coupon (discount, time-boxed free entitlement) is fundamentally a billing/entitlement
concept. Redeeming one is a keep operation; the resulting entitlement change reaches tower
exactly the way every other keep-originated change already does — the existing async
materialization path (ADR 0001/0006/0018). Tower needs no `coupon` actor and no new mechanism.

**Flagged, not designed:** a single marketing code that should grant *both* access (invite) and
a discount (coupon) in one redemption is plausible (e.g. `LAUNCH50` meaning both "let me in"
and "50% off"). Whether that's two coordinated redemptions orchestrated by `web`, or something
that needs a real cross-service design, is an open question for whenever keep's coupon model
actually gets designed — not resolved here. **Resolved by
[ADR 0039](0039-keep-trials-and-coupons.md)**, once keep's `coupon` actor existed to answer it:
no new cross-service mechanism — a `web`/admin-level convention of creating a matching
`inviteCode` and `coupon` sharing the same code string, checked by the redemption flow. This
ADR's own text never got a pointer back to that resolution; added now.

## Consequences

- New `inviteCode` actor in tower; no changes needed to portcullis or any proxy story — this is
  entirely a tower/`web`-side concern.
- `permissions` (ADR 0018) is now understood as a general capability-grant primitive, not
  strictly an admin-operations concept — worth keeping in mind for any future permission grants
  beyond the ones enumerated so far.
